現在の目的は、ChatGPTのGPT-5.6 Sol ProをAPI従量課金で都度利用する代わりに、すでに契約しているAIサブスクリプション、特にGitHub Copilot Maxの利用枠を活用して、Proで得られている実用上の価値に近いものを再現できる仕組みを検証・構築することにある。

背景として、ChatGPT Plus + OpenAI APIで`reasoning.mode: "pro"`を利用する運用を実際に試したところ、Proを使いたい程度に難しい質問では1回あたり概ね$2〜3程度を消費している。この従量課金を毎回追加で負担することが経済的な問題であり、単純に1回あたりの理論的な計算コストを$2〜3未満へ抑えること自体が目的ではない。すでに支払っているサブスクリプション枠、GitHub Copilot MaxのAI Credits、その他の定額利用枠を消費するのであれば、内部的・換算上はより高コストでも許容できる。

Proに求めている価値も、単に通常のGPT-5.6 Solより「頭の良い単一モデル」を使うことではない。実際の使用感として重要なのは、難しく曖昧な問題に対して一つの初期仮説や解釈へ過度にアンカリングせず、別の観点や代替仮説を検討し、最初の方向性そのものを疑い、反証や見落としを探し、それらを比較したうえで最終判断をまとめることである。結果として、「検討が特定のずれた方向へ偏ったまま高度に詳細化される」「一度外れた推論経路をそのまま走り続ける」といった大外しを減らし、一度の依頼で安定して妥当な回答へ到達する確率を高めたい。

この要求は、Proの内部実装そのものを再現することとは区別する。Proの正確な内部アーキテクチャを模倣する必要はなく、欲しいのはその実用上の効果、すなわち難問に対する推論のロバスト性である。現在の整理では、その価値を「独立した複数の仮説・観点を生成すること」「初期案とは独立した再検討を行うこと」「反証・失敗条件・見落としを探すこと」「複数結果を比較して最終判断すること」「一発での大外しを減らすこと」と捉えている。

この目的に対する最初の実験基盤としては、GitHub Copilot SDKを使った明示的なfan-out / fan-in構成を採用する方針で合意している。これは、GitHub Copilot Maxの契約枠の中で複数モデルを利用でき、GPT-5.6 Solだけでなく別系統のモデルへ切り替えた場合の効果も同じ基盤上で比較できるため、初期実験としてバランスが良いという判断による。

初期段階では、複数の独立したCopilot SDK sessionを明示的に起動し、同一の元質問に対して互いの回答を見せずに分析させ、その結果を後段で比較・統合する構成を基本とする。重要なのは単に複数agentを実行することではなく、最初の分析段階で相互に回答を見せず、初期のアンカリングを共有させないことである。したがって、最初からGroup Chat形式で互いの発言を読みながら議論させる方式は、今回の中心目的には適さない。必要に応じて後段で意見の不一致点だけを再検討・批評させることは候補に残るが、独立分析を先に行うという構造は維持する。

現時点での中心的な構成イメージは、複数の独立analystが同じ問題を別々に分析し、その後に結果間の不一致・前提差・見落としを抽出し、必要ならcriticによる追加検討を行い、最後にarbiterが一つの回答へ統合するものである。多数決で結論を決めることは目的ではなく、それぞれの根拠・前提・反証を評価したうえで最終判断する必要がある。

GitHub Copilot SDKを最初の実験基盤として選ぶことは決まっているが、初期実験で使用する具体的なモデル構成はまだ固定していない。GPT-5.6 Solを複数役割で使う場合、ClaudeやGeminiなど異なるモデル系列を混ぜる場合、それぞれの効果を比較できること自体が今回Copilotを選んだ理由の一つである。したがって、どのモデルをanalyst、critic、arbiterに割り当てるかは今後の設計・実験対象であり、現時点で特定モデル構成を固定要件として扱わない。

また、この推論手順をSKILLとして表現する案は有力だが、SKILLだけにすべてを委ねる方針は採用していない。SKILLは「独立分析、disagreement analysis、challenge、arbitration」といったPro-likeな推論プロトコルや各役割の手順を定義する用途には適している。一方で、独立sessionの生成、fan-out、fan-in、相互に回答を見せないという実行上の分離は、SKILLの指示に任せるのではなくオーケストレータ側で保証する方針が望ましい。SKILLを実際にどの粒度・形式で作るかは未確定である。

Microsoft Agent Frameworkなどの本格的なマルチエージェント基盤を最初から採用することは、現時点では決定していない。将来的にGitHub Copilot以外のサブスクリプション枠やproviderも一つのシステムから束ねる価値が確認できた場合には有力候補となるが、まずはCopilot SDKだけで十分に小さく実験し、Proで感じているロバスト性がどの程度再現できるかを確認する。システム構築自体を目的化しないことが重要である。

手元にはChatGPT Plus、GitHub Copilot、SuperGrok、OpenCode Goなどの契約があり、将来的にはこれらを異なるanalystやcriticとして組み合わせる可能性がある。ただし、現段階のゴールは最初から全サブスクリプションを統合することではない。まずGitHub Copilot内で複数model・複数独立sessionによる構成を作り、モデル多様性や独立レビューがPro-likeな安定性にどの程度寄与するかを評価する。それで有効性が確認できた場合にのみ、SuperGrok、OpenCode Go、ChatGPT Plus/Codexなど外部の定額枠を追加する価値を検討する。

最初の実験で成功とみなすべき観点は、単なる回答品質やベンチマーク点数の上昇ではない。同じ種類の重要・曖昧な質問に対し、通常の単一Solでは一方向へ偏ってしまうケースで、複数独立分析と統合を行う構成が、別の有力仮説・反証・前提の誤りを拾い、最終回答の大外しや偏った一本道を実際に減らせることが重要である。本物のSol Proと完全一致する必要はなく、「Proを使いたい」と感じる種類の質問に対して、追加API課金をせず既存のCopilot契約枠を主に使いながら、実用上十分近い信頼性を得られるかを確かめることが評価の中心となる。

未解決の事項としては、独立analystの人数、各stageの具体的な役割、使用モデルの割り当て、disagreementの検出方法、criticを追加実行する条件、arbiterへ渡す情報量、SKILLとコード側責務の境界、実験結果を本物のProとどう比較評価するかが残っている。これらは今後の設計対象であり、現段階では固定要件として扱わない。

高位の目的はあくまで、「GPT-5.6 Sol Proというモデルを模倣すること」ではなく、「難しい問題で一つの誤った推論経路へ偏りにくく、複数観点を独立に検討・批評・統合して一度の依頼で安定した結論へ到達する」というProで感じている実用上の価値を、既存のサブスクリプション資産を活用して再現できる仕組みを見つけることである。
